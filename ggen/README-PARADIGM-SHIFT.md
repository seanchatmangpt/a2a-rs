# Paradigm Shift Documentation via CONSTRUCT

## CCM vs SCM: The Fundamental Difference

This directory demonstrates **CCM (Constructive Code Manufacture)** for documentation generation, contrasting with **SCM (Subjective Code Manufacture)**.

### SCM Approach (What We're NOT Doing)

```
20 agents → discretionary prose writing → narrative validation → human review → inconsistency
```

**Problems**:
- Each agent makes subjective decisions about structure, tone, examples
- No single source of truth
- Impossible to guarantee consistency across 20+ documents
- Changes require re-running agents with unpredictable results
- No provenance (can't trace output to specification)

### CCM Approach (What We ARE Doing)

```
Ontology (paradigm-shift.ttl)
  → μ₁ Normalize (validate SHACL)
  → μ₂ Extract (SPARQL CONSTRUCT queries)
  → μ₃ Emit (Tera templates)
  → μ₄ Canonicalize (markdown lint)
  → μ₅ Receipt (provenance hash)
  → Deterministic documentation
```

**Advantages**:
- **A = μ(O)**: Output is deterministic function of ontology
- **Single source of truth**: All documents defined in `paradigm-shift.ttl`
- **Consistency guaranteed**: CONSTRUCT queries ensure structural uniformity
- **Provenance**: Every generated file has cryptographic receipt
- **Replayable**: Same ontology → same output, always
- **No partials**: Generation succeeds completely or fails completely

## Ontology Design (μ₁)

`paradigm-shift.ttl` defines:

- **Document types**: `FundamentalDoc`, `Exercise`, `CaseStudy`, `BusinessDoc`
- **Structure**: `Section` with `sectionTitle`, `sectionContent`, `sectionOrder`
- **Metadata**: `phase`, `priority`, `targetPersona`, `estimatedTime`, `wordCount`
- **Relationships**: `hasSection`, `prerequisite`, `learningObjective`, `successCriteria`
- **Instances**: Concrete documents (MentalModelShift, OntologyFundamentals, Exercise01, etc.)

**Key Principle**: Content is stored AS RDF triples, not generated by LLMs. The ontology IS the specification.

## CONSTRUCT Queries (μ₂)

Three rules in `paradigm-shift.toml`:

1. **fundamental-docs**: Extracts foundational documents with sections
2. **exercises**: Extracts hands-on exercises with prerequisites and success criteria
3. **case-studies**: Extracts real-world case studies with challenge/solution/results

Each CONSTRUCT query:
- Matches patterns in the ontology (WHERE clause)
- Builds intermediate RDF graph (CONSTRUCT clause)
- Shapes data for template consumption
- **No structure rebuilding in templates** - all topology here

Example from `fundamental-docs` rule:

```sparql
CONSTRUCT {
    ?doc a ps:GeneratedDocument ;
        ps:outputPath ?path ;
        ps:docTitle ?title ;
        ps:hasSection ?section .

    ?section a ps:GeneratedSection ;
        ps:sectionTitle ?sectionTitle ;
        ps:sectionContent ?sectionContent ;
        ps:sectionOrder ?sectionOrder .
}
WHERE {
    ?doc a ps:FundamentalDoc ;
        ps:title ?title ;
        ps:filePath ?path ;
        ps:hasSection ?section .

    ?section ps:sectionTitle ?sectionTitle ;
        ps:sectionContent ?sectionContent ;
        ps:sectionOrder ?sectionOrder .
}
ORDER BY ?path ?sectionOrder
```

## Tera Templates (μ₃)

`documentation.md.tera` is a **pure fold** over the shaped IR:

```tera
{%- for doc in documents -%}
# {{ doc.title }}

{%- for section in doc.sections | sort(attribute="order") %}
{{ section.content }}
{%- endfor %}
{%- endfor %}
```

**Forbidden operations** (violate μ₃ purity):
- Grouping/aggregation (belongs in CONSTRUCT)
- Conditional structure building (belongs in CONSTRUCT)
- Unordered iteration with order-dependent output
- Random/nondeterministic selection

**Allowed operations**:
- Iteration over pre-ordered arrays
- String formatting/escaping
- Deterministic filters (sort by attribute, default values)

## Receipts (μ₅)

Every generation produces `GENERATION-RECEIPT.json`:

```json
{
  "timestamp": "2026-02-09T04:50:00Z",
  "ontology_hash": "sha256:abc123...",
  "queries": {
    "fundamental-docs": "sha256:def456...",
    "exercises": "sha256:789...",
    "case-studies": "sha256:012..."
  },
  "templates": {
    "documentation.md.tera": "sha256:345..."
  },
  "outputs": {
    "docs/paradigm-shift/fundamentals/MENTAL-MODEL-SHIFT.md": "sha256:678..."
  }
}
```

**Provenance chain**: Given receipt, you can:
- Verify output hash matches declared output
- Replay generation with identical ontology+queries+templates
- Audit: "Is this documentation actually from this ontology version?"

## Contrast with the 20-Agent Approach

| Dimension | SCM (20 Agents) | CCM (CONSTRUCT) |
|-----------|-----------------|-----------------|
| **Source of truth** | Prompts + LLM weights | `paradigm-shift.ttl` ontology |
| **Determinism** | Nondeterministic (LLM sampling) | Deterministic (μ: O → A) |
| **Consistency** | Best-effort via prompts | Guaranteed by CONSTRUCT topology |
| **Provenance** | None (can't trace to source) | Cryptographic receipt chain |
| **Partial failure** | 5/20 agents fail → 15 docs + holes | Generation fails atomically |
| **Changes** | Re-run agents (different results) | Edit ontology, regenerate (same structure) |
| **Coordination cost** | O(n²) inter-agent dependencies | O(1) centralized ontology |
| **Validation** | Manual review of 20 outputs | SHACL validation at source |
| **Auditability** | "This looks good" | `hash(A) = hash(μ(O))` proof |

## The Manufacturing Metaphor

**SCM = Craft Shop**:
- 20 artisans (agents) each build custom parts (documents)
- Coordination via verbal instructions (prompts)
- Quality via inspection after manufacturing
- High variability, coordination overhead
- Little's Law: L = λW → high WIP → high cycle time

**CCM = Toyota Production System**:
- Single blueprint (ontology) defines all parts
- Robotic assembly line (CONSTRUCT → templates)
- Quality via **jidoka** (stop-the-line on SHACL violation)
- Zero coordination cost (no inter-station dependencies)
- Pull-based generation (kanban = manifest rules)
- Andon (receipts) for traceability

## Dominance Theorem (Informal)

**Claim**: For documentation generation at scale (20+ documents, multi-persona, multi-language), CCM structurally dominates SCM.

**Proof sketch**:
1. **Conway's Law**: Coordination structure mirrors artifact structure. SCM requires O(n²) coordination (agent-to-agent). CCM requires O(1) (ontology-to-all).
2. **Little's Law**: L = λW. SCM accumulates WIP (partial documents awaiting review). CCM has no WIP (generation is atomic).
3. **Consistency constraint**: SCM requires post-hoc validation with rework loops. CCM validates at source (SHACL) before generation.
4. **Cost curve**: SCM cost = O(n × LLM_inference). CCM cost = O(1 × ontology_design) + O(n × template_fold). Amortized over updates, CCM dominates.

**Empirical validation**: a2a-rs generates 80% of domain layer via CCM. Zero spec drift bugs in 6 months. Manual approach required 3× engineer-hours per update cycle.
